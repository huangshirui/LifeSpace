# Space-local External Models / 空间外部模型

Status: staging candidate implementation contract for Federated Truth / External Data; not a production capability until canonical staging and production release gates pass.

External Model is a **Query** relationship to provider-authoritative Shared World/Knowledge. Core owns Semantics, Authority and Context Projection (A1/A3/A5); the provider owns record payload/schema. Core never mirrors external business records.

## External business definition and Space binding / 外部业务定义与空间绑定

External models first publish a provider-neutral business definition through the existing Model Registry / Console Model publishing flow. The closed definition declares `origin: external`, stable business `key`, display/description, access ceiling and outgoing Semantic Relations, with `fields: {}`. It does not prescribe or mirror provider fields, generate a Native table, or inherit Native Actions/Capabilities/concurrency. Other model definitions can declare this stable key as a relation target before any Provider Resource is bound.

A Space then binds that published External definition to an existing Dynamic Connection and concrete Provider Resource. One active binding per `(spaceId, definitionKey)` is allowed; one Provider Resource belongs to exactly one source Space. The public model address and Authority key are the stable business key; `ext_*` remains the binding identity. Unbound/disabled/retired definitions never create runtime availability or Authority. A Native model cannot change origin to External or vice versa.

Provider schema discovery is automatic and latest-only. The immutable Registry contract pins business semantics only; External field/wire constraints remain dynamic and must be read from Space Discovery. A description/type declaration cannot change Provider fields or grant access. Model definition registration uses the existing actor-aware Platform Admin Model governance path for Console and the independent Service Automation Model Control Plane for non-interactive automation. Space binding has one canonical Core state with two explicit authority surfaces: downstream applications may use direct User + Space-management authority, while LifeSpace Console uses Platform Admin actor proof + controlled Core executor. Neither path creates hidden platform membership.

`Space Model Catalog = global active Native Models + active External bindings for this Space`. External binding IDs reserve `ext_<32 hex>`; business runtime keys come from the published External definition. Native publication cannot use `ext_`. Provider/resource identity is unique across connections and Spaces, including disabled bindings. Rebinding the same disabled Provider Resource in the same Space restores that identity; it never moves it to another Space. Active duplicate binding is a conflict. Disable removes runtime availability without deleting Provider data or old Grants. Connections are execution connections, not ACLs.

Native resolution retains its isolate descriptor path with zero additional D1/HTTP tax. External resolution checks current binding/Connection status and reads the latest compatible snapshot. Immutable Registry/mct pins business definitions; Provider fields stay latest-only and dynamic. External detail binds `(spaceId,modelKey,schemaHash)` and has no Native model version.

## Connections, Provider routing and credentials / 连接、Provider 路由与凭据

There is one authoritative External Connection/binding implementation and one private Adapter credential owner, but two deliberate administration surfaces over that same state:

```text
Downstream application self-service
User + spaces:manage + current Space manage
-> /api/v1/spaces/{spaceId}/external-*

LifeSpace Console governance
platform_admin_actor + controlled Core executor
-> /api/v1/platform-admin/spaces/{spaceId}/external-*
```

The public Space-scoped `apps/core/external-connection.openapi.yaml` **0.4.0** remains the canonical application self-service contract. The Platform Admin contract reuses its request/response schemas and the same Core implementation/state; it is not a second External protocol or persistence layer. Both surfaces may create/list/update/revoke External Connections, discover Provider resources, list/update/disable bindings, inspect the latest stored binding schema snapshot and refresh binding schema when their respective authority checks pass. Binding-detail inspection is configuration-only: it reads Core's persisted latest snapshot, does not call the Provider, and is not runtime execution authority. Runtime consumers still use Space Discovery for current dynamic field semantics. The client submits Provider credential material only on Connection creation or rotation; it can never choose or read a `credentialRef`.

External is provider-neutral at the Core boundary. Deployment owns `EXTERNAL_PROVIDER_ROUTES`, which maps `providerKey` to one Provider-specific private Service Binding and one Provider-specific Core→Adapter transport secret. Notion is the first route (`EXTERNAL_ADAPTER_NOTION` + `EXTERNAL_ADAPTER_NOTION_SHARED_SECRET`); adding another Provider does not change the public Connection/binding/runtime API. Runtime dispatch uses persisted `provider_key`; Provider-specific credential/schema translation remains inside that Provider Adapter. Canonical staging/production verification rejects a generic remote Adapter Service Binding.

Core generates an opaque `cnx_*` reference and forwards credential plaintext transiently only to the selected private Provider Adapter. Provider credential plaintext is never persisted in Core D1, Model Registry, audit, Console Worker state or API responses. Each Provider Adapter owns its credential vault. The Notion Adapter maps every `cnx_*` to one `NotionConnectionVault` Durable Object. Before DO persistence, the connection credential projection is encrypted with AES-256-GCM under that Adapter's vault master key; Durable Object storage contains only a versioned `{version,algorithm,iv,ciphertext}` envelope. Plaintext exists only transiently during one DO operation and is not cached across warm requests. Existing pre-encryption DO state is supported only as a one-way lazy migration. Missing/invalid/mismatched vault keys fail closed. Core D1 stores only Space-scoped connection metadata, provider key, status/access ceiling and the opaque reference.

The Adapter accepts only Core-generated `cnx_*` references. Deployment-managed static credential maps such as the retired `NOTION_CONNECTIONS` mechanism are not supported. Core no longer exposes a service-only `/api/v1/model-admin/external-sources` source-provisioning API or a Space `/external-sources` compatibility control path. There is one Connection lifecycle and one credential owner.

Connection access is a hard platform ceiling. Binding creation and later `read → write` elevation must satisfy both the current Connection ceiling and the current published External Model Definition ceiling. Schema 64 also enforces `Connection write → read` at the D1 layer: all attached write bindings are synchronously narrowed to read, so future/control-plane callers cannot bypass the invariant. A binding whose published Definition is unavailable/retired cannot be raised to write. Revocation deletes the Adapter vault first, then marks the Core Connection revoked/disabled and parks its bindings. Provider access removal fails closed.

Creating or governing a Connection grants no Application × Model Access, Membership, Data Grant or model binding. Application-side External setup uses direct User Space-management Authority. Console-side External setup uses Platform Admin authority and records the human actor plus service executor; it does **not** borrow ordinary User/Space authority and does not make either actor or executor a hidden Space member. Runtime uses the **same** current Application × Model Access, Membership/Data Grant, scope and Delegation functions as Native regardless of which control-plane surface configured the Connection/binding.

## Adapter contract / 适配器契约

Canonical internal runtime contract: `apps/core/external-adapter.contract.json`, version `1`. After Provider routing selects the Adapter, a POST to its fixed `/internal/v1/external-models` endpoint accepts providerKey, `cnx_*` credentialRef, operation, resourceId and the latest compatible snapshot. It returns normalized data or a bounded generic error code. Provider messages/bodies/headers never enter client errors or audit.

Canonical internal Connection-management contract: `apps/core/external-connection-adapter.contract.json`, version `1`. Core routes by `providerKey`, then calls that Adapter's fixed `/internal/v1/external-connections` endpoint for provider descriptor discovery, connection create/update/delete and bounded resource listing. The Adapter owns credential persistence/encryption and Provider-specific validation; Core owns Space Authority, routing and Connection metadata. Neither contract permits caller-controlled Adapter URLs.

Provider transport secrets and Provider vault master keys are independent per Provider. `EXTERNAL_CURSOR_SECRET` is a separate Core-only HMAC secret for opaque External pagination and must not reuse any Provider transport secret, vault key, bootstrap secret or Provider token. Staging and production use different secret sets. Replacing a vault master key in place is not a valid rotation procedure while old ciphertext remains; rotation requires versioned decrypt/re-encrypt migration or explicit credential reconnection.

Snapshot contains only supported fields. Its field definition uses the **same LifeSpace Canonical Field Language as Native models** (`CanonicalFieldType` plus applicable canonical constraints); External does not own a second type enum or provider-independent type allowlist. The Adapter may emit Provider-provisional field keys during discovery, but `sourceFieldId` is the durable Provider identity. Core then assigns a legal Native-style public Field Key, persists `sourceFieldId -> key` independently from the latest snapshot, and reuses that key across schema refreshes. Provider rename therefore updates `title`/`description` while the public key stays stable; delete/recreate with a new `sourceFieldId` creates a new identity instead of inheriting a same-name field accidentally. `sourceFieldId` and private bounded `adapterState` are never exposed as ordinary Record field names.

Adapters expose only canonical fields for which they can provide a **stable deterministic canonical semantic projection**. Shape-level losslessness is not required: Provider presentation/implementation metadata may be discarded, but business meaning may not be fabricated or silently changed. Provider fields without a stable projection remain absent instead of leaking Provider-native JSON/types into Core. For a supported field, the Adapter defines how missing/unavailable Provider values project without turning one weak-schema value into a whole-record failure. Read/filter/sort for a field must share the same projection semantics. A schema hash identifies the current canonical semantics, not a revision history.

Every Provider Adapter MUST review schema compatibility on three independent axes and document the result next to that Adapter:

1. **Type Mapping** — Provider field type → Canonical Field Type, including unsupported Provider types;
2. **Metadata Mapping** — each relevant Canonical `FieldDefinition` metadata property (`title`, `description`, `required`, `nullable`, `immutable`, `readOnly`, length/numeric constraints, `values`, `targetModel`, etc.) is classified as **provider-native**, **adapter-derived**, **unsupported**, or **provider-only**;
3. **Stable Identity Mapping** — which Provider identifier is the durable `sourceFieldId`, how Core obtains a stable public `key`, and how rename/delete/recreate behave.

A type-only compatibility table is therefore insufficient for a new External Provider. Provider-specific UI/implementation metadata may stay Provider-only, but an Adapter must make that omission explicit rather than silently treating absent metadata as a Canonical guarantee.

The Canonical Field Language includes provider-neutral collection/reference value types such as `enum_list` and `file_ref_list`. `file_ref_list` represents references (`name`, `url`, optional `expiresAt`) rather than mirrored bytes; Provider-hosted content remains at the Provider unless a separate product explicitly performs a copy. Native legacy scalar query transport does not infer JSON-list filtering for these types; an External Adapter may advertise bounded Provider-native operators such as multi-enum `contains` when it can execute them efficiently.

Read/query/write use the same `/models/{modelKey}/records` paths. Ordinary record responses use the same public record identity envelope as Native where the Provider can support it honestly: `id,spaceId,modelKey`, flattened canonical fields, and real Provider timestamps when available. Provider/storage identity metadata such as `origin` and `schemaHash` is confined to Discovery/configuration/internal execution and is not returned on ordinary CRUD/Query records; Native-only `modelVersion/version/createdBy/updatedBy` is never fabricated. Query pushes a declared typed subset to the Provider and rejects unsupported operators/values. No unbounded scans. Opaque authenticated cursor binds Space/model/schema/query/provider continuation internally. Pagination is live, not a snapshot; Provider sorting/null placement/tie behavior is explicitly Provider-defined rather than Native-guaranteed.

## Capability and change boundary / 能力与变更边界

get/query/create/update/delete and bounded per-item bulk may be supported. `atomicBatch`, `transaction`, `versionedWrite`, `actions`, Native Eventing and Native record history are false. Caller-supplied version is rejected. Unified `/models/batch` accepts External CRUD with explicit `atomicConsistency=false` and optional request-wide `delegationId`; atomic/default requests reject before any write. `/models/bulk` remains compatible. Mixed Native/External CRUD requests retain per-item semantics with no distributed transaction; independent relation_create/relation_delete actions can follow Provider CRUD in an explicitly non-atomic request. Request-local create clientRefs resolve after successful record creation; failed or unknown creates fail dependent relations. Provider record writes and D1 edges do not roll back together. Attached semanticRelations on a Provider create remain unavailable; use independent relation_create.

External operation audit is `pending -> succeeded | failed | unknown`. It captures verified Application/Principal/Actor/Delegation chain, operation, identity, timestamp and status; no record payload, secret or historical schema. Write audit is persisted **before** Provider execution. Crash/network ambiguity remains pending/unknown; it is never reported as a guaranteed failure and never retried blindly. This is operation attribution, not Native Change/outbox or Information Provenance. Single-use delegated writes are rejected because Provider success and D1 consumption cannot be atomically guaranteed. Single-use reads use the existing conditional consumption before returning data.

## Freshness and failures / 新鲜度与失败

Binding discovers once; manual refresh and a bounded scheduled reconciliation update only the latest snapshot. External runtime requires deployment-supplied `EXTERNAL_SCHEMA_REFRESH_SECONDS` (60–86400); no speculative default SLO is presented as measured. Reconciliation selects at most 20 executable due bindings through the partial next_refresh_at/model_key index, with 2 concurrent refreshes. Disabling a Connection or retiring its business definition parks its queue entries. Connection, Space and business-definition liveness filter before LIMIT. Republishing the same origin resumes eligible binding/identity queues without resetting Registry versions or deleting records. External reconciliation, Recurrence rolling and existing outbox dispatch run with independent failure isolation; all failures remain observable. No ordinary operation fetches schema first. An explicitly unexecuted schema-mismatch response permits one refresh and one retry; uncertain writes never retry. Metadata status uses current-state checks. Provider access removal and Connection revoke fail closed.

For non-atomic relation batches, a Provider endpoint read failure belongs to the items depending on that endpoint. Independent Native mutations and successful endpoint items continue; Get/Query retain their strict failure semantics. Provider read audit and degraded metadata finalize in grouped D1 writes rather than one D1 update per failed endpoint.

## Relations / 关系

Published, active External business bindings participate in the same Semantic Relation API using business model keys. Source write and target read are checked before Provider resolution; grouped identity-only metadata, pending/final audit batches and <=3 concurrent Provider reads avoid per-endpoint D1 waterfalls. Native-Native commit/cleanup remains atomic. External endpoints reject atomic batch before Provider I/O, expose opaque unavailable on failed/missing hydration, and never invent Native versions. Confirmed through-LifeSpace Provider deletion invalidates observed identity and cleans local edges afterward; this local cleanup is not atomic with the Provider write. Provider-direct absence remains opaque: missing and denied cannot reliably prove deletion, so retained links can be explicitly removed under current source-write/target-read authority without contacting the Provider. Bounded periodic identity observation checks at most 20 due IDs with <=3 concurrent Provider reads, stores only availability/observation/next-check metadata, and marks missing/hidden endpoints unavailable before SQL pagination. It uses the trusted Connection only for metadata observation, never saved User/Delegation tokens, and publishes no Provider payload or fabricated User attribution. Links are retained for explicit local removal; successful later reads restore availability. Queue indexes and Connection/binding parking keep disabled Connections out of executable work. Actual Provider latency/freshness remains a staging gate. Fixed record/record_list field targets remain Native-only.

## Verification and rollout / 验证与发布

Synthetic contract/integration tests and structural call-count tests are reproducible. Provider wall latency/freshness SLO, real credential permissions and staging acceptance require isolated deployed Provider Adapter bindings and synthetic Provider resources. Local timings are not Provider p50/p95. No production docs may mark this available before successful production deployment.

Deployment wiring is code-owned by the canonical manual platform workflows and `infra/external-provider.json`. An enabled environment deploys each pinned Provider Adapter before Core, generates Provider-specific Core Service Bindings plus `EXTERNAL_PROVIDER_ROUTES`, injects independent Core cursor / Provider transport / Provider vault secrets over stdin, and verifies private exposure, Provider-specific routing, schema refresh configuration and required vault bindings. Remote profiles explicitly configure a 300-second schema refresh interval; this is configuration, not a measured SLO.

Staging has **one** External product gate. A staging-only `NOTION_SMOKE_TOKEN` is held by the GitHub `staging` Environment and is supplied only as request input to the public Dynamic Connection API during acceptance. It is never deployed as a Worker static credential map and is never persisted by Core. The gate proves Provider discovery → Connection create → encrypted DO Vault → Provider Resource discovery → binding → Runtime CRUD/query → Connection access downgrade and synchronous binding narrowing → credential rotation → disable/enable → revoke/cleanup. `LIFESPACE_EXTERNAL_SMOKE_RESOURCE_ID` identifies the dedicated synthetic resource and `LIFESPACE_EXTERNAL_SMOKE_SYNTHETIC_CONFIRMED=1` is the destructive-test safety gate. Production has no Provider smoke token. See [deployment prerequisites and acceptance](../infra/external-provider-rollout.md).

Console is a first-party **Platform Admin proving client**, not a second control plane. A Space exposes exactly one standard `Configure → External data` surface. Its Connection tab owns Connection lifecycle; its Model Binding tab owns binding create/list, stored latest-schema inspection, schema refresh, read/write ceiling changes and disable. Stored-schema inspection is lazy/read-only, uses Platform Admin authority in Console, never calls the Provider and never substitutes for Runtime Discovery. Disabled bindings are restored through the same normal re-bind flow so Provider identity/schema are revalidated; there is no second `External bindings` fallback UI/BFF.

The same canonical External state remains available to ALOHA, HomeMew and other applications through the ordinary Space-scoped API 0.4.0 contract under User/Space authority. Console does not use that ordinary authority path: it exchanges the verified Access principal only to identify/re-authorize the human Platform Admin, obtains a short-lived `purpose=platform_admin_actor` proof, and calls the `/api/v1/platform-admin/spaces/{spaceId}/external-*` companion routes using the bounded Console Core executor. Console Application/executor scope ceilings must explicitly allow the control-plane scopes required by those routes; this does not create a Data Grant or record-access right for Console. Provisioning and real staging verification are release gates.
