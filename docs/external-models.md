# Space-local External Models / 空间外部模型

Status: implementation contract for #340; not a production capability.

External Model is a **Query** relationship to provider-authoritative Shared World/Knowledge. Core owns Semantics, Authority and Context Projection (A1/A3/A5); the provider owns record payload/schema. Core never mirrors external business records.

## Identity and lifecycle / 身份与生命周期

## External business definition and Space binding / 外部业务定义与空间绑定（开发中）

External models first publish a provider-neutral business definition through the existing Model Registry / Console Model publishing flow. The closed definition declares `origin: external`, stable business `key`, display/description, access ceiling and outgoing Semantic Relations, with `fields: {}`. It does not prescribe or mirror provider fields, generate a native table, or inherit Native Actions/Capabilities/concurrency. Other model definitions can declare this stable key as a relation target before any database is bound.

A Space then binds that published External definition to an existing Connection and concrete Provider Data Source. One active binding per `(spaceId, definitionKey)` is allowed; one provider resource still belongs to exactly one source Space. The public model address and Authority key are the stable business key; `ext_*` remains the binding identity. Unbound/disabled/retired definitions never create runtime availability or Authority. Legacy untyped registrations keep their explicit `ext_*` CRUD addressing; type-constrained relations require a published business definition and binding. A Native model cannot change origin to External or vice versa.

Provider schema discovery remains automatic and latest-only. The immutable Registry contract pins business semantics only; External field/wire constraints remain dynamic and must be read from Space Discovery. A description/type declaration cannot change provider fields or grant access. Model definition registration uses the existing actor-aware Model Admin boundary; Space binding uses the existing direct User Space-management boundary, without hidden platform membership.

`Space Model Catalog = global active Native Models + active External registrations for this Space`. External binding IDs reserve `ext_<32 hex>`; business runtime keys come from the published External definition. Native publication cannot use `ext_`. Identity is unrelated to display name. Provider/resource identity is unique across **all** connections and Spaces, including disabled registrations. Re-registration in the same Space restores a disabled identity, never moves it to another Space. Active duplicate registration is a conflict. Disable removes runtime availability without deleting provider data or old Grants. Connections are configured under a managing Space; they are execution connections, not ACLs.

Native resolver retains its isolate descriptor path with zero additional D1/HTTP tax. External resolution checks current registration/connection status and reads the latest compatible snapshot. Immutable Registry/mct pins business definitions; Provider fields stay latest-only and dynamic. External detail binds `(spaceId,modelKey,schemaHash)` and has no Native model version.

## Connections and credentials / 连接与凭据

The normal product path is the public Space-scoped `apps/core/external-connection.openapi.yaml` contract. Console and downstream applications are equivalent clients: a direct User with `spaces:manage` plus current Space `manage` may create/list/update/revoke External Connections and discover Provider resources. The client submits provider credential material only on connection creation or rotation; it can never choose or read a `credentialRef`.

Core generates an opaque `cnx_*` reference and forwards the credential transiently over the fixed private `EXTERNAL_ADAPTER` Service Binding, authenticated with the independent shared Secret. Provider credential plaintext is never persisted in Core D1, Model Registry, audit, Console Worker state or API responses. The private Adapter validates the credential and maps each dynamic `cnx_*` to one provider-owned `NotionConnectionVault` Durable Object. Before DO persistence, the connection credential projection is encrypted with AES-256-GCM under the Adapter-only `CONNECTION_VAULT_MASTER_KEY`; Durable Object storage contains only a versioned `{version,algorithm,iv,ciphertext}` envelope. Plaintext exists only transiently in that Connection DO execution memory while validating or calling the provider. Existing pre-encryption `{token,read,write}` DO state is supported only through one-way lazy migration: first successful read encrypts and replaces it before execution continues. Missing/invalid/mismatched vault keys fail closed. Core D1 stores only Space-scoped connection metadata, provider key, status/access ceiling and the opaque reference. Dynamic revocation deletes the Adapter vault first, then marks the Core connection revoked/disabled and parks its bindings. Provider access removal fails closed.

`NOTION_CONNECTIONS` and `/api/v1/model-admin/external-sources` remain deployment/bootstrap compatibility mechanisms for synthetic acceptance and controlled legacy connections. They are **not** the normal application configuration API. Staging requires one synthetic static connection for automatic smoke; production may run dynamic-only and canonical deployment writes an explicit empty `{}` static map when no bootstrap map is configured so stale static references cannot linger. A service Model Admin may provision a deployment-managed connection only from such a server-owned reference; ordinary callers cannot guess or mutate that reference. Deployment-managed connections may be listed/enabled/disabled through Space management but their credential cannot be rotated/deleted or used for product resource discovery through the dynamic Connection API.

Creating a Connection grants no Application × Model Access, Membership, Data Grant or model binding. External Model registration/refresh/disable and Connection configuration all use the existing direct-User Space-management boundary. Runtime uses the **same** current Application × Model Access, Membership/Data Grant, scope and Delegation functions as Native.

## Adapter contract / 适配器契约

Canonical internal runtime contract: `apps/core/external-adapter.contract.json`, version `1`. A POST to the fixed `/internal/v1/external-models` accepts providerKey, credentialRef, operation, resourceId and the latest compatible snapshot. It returns normalized data or a bounded generic error code. Provider messages/bodies/headers never enter client errors or audit.

Canonical internal Connection-management contract: `apps/core/external-connection-adapter.contract.json`, version `1`. Core alone calls the fixed `/internal/v1/external-connections` endpoint for provider descriptor discovery, connection create/update/delete and bounded resource listing. The Adapter owns credential persistence/encryption and provider-specific validation; Core owns Space Authority and connection metadata. Neither contract permits caller-controlled adapter URLs. `CONNECTION_VAULT_MASTER_KEY` is Adapter-only, independent from `EXTERNAL_ADAPTER_SHARED_SECRET`, bootstrap secrets and provider tokens, and staging/production use different keys. Replacing this master key in place is not a valid rotation procedure while old ciphertext remains; rotation requires versioned decrypt/re-encrypt migration or explicit credential reconnection.

Snapshot contains only supported fields: stable canonical key, source field identity, canonical type, title, nullable/readable/writable/filter operators/sortable and optional enum values. Private bounded `adapterState` holds codecs for **supported** fields only; it is never exposed by Discovery. Unsupported fields do not appear anywhere in the LifeSpace model. Stable source property identity survives rename; types are automatically replaced, without request/data coercion. A schema hash identifies current semantics, not a revision history.

Read/query/write use the same `/models/{modelKey}/records` paths. Response is an external envelope (`id,spaceId,modelKey,origin,schemaHash,data fields,provider timestamps`); it omits fabricated version/createdBy/updatedBy. Query pushes a declared typed subset to the provider and rejects unsupported operators/values. No unbounded scans. Opaque authenticated cursor binds Space/model/schema/query/provider continuation. Pagination is live, not a snapshot; provider sorting/null placement/tie behavior is explicitly provider-defined rather than Native-guaranteed.

## Capability and change boundary / 能力与变更边界

get/query/create/update/delete and bounded per-item bulk may be supported. `atomicBatch`, `transaction`, `versionedWrite`, `actions`, Native Eventing and Native record history are false. Caller-supplied version is rejected. Unified `/models/batch` accepts External CRUD with explicit `atomicConsistency=false` and optional request-wide `delegationId`; atomic/default requests reject before any write. `/models/bulk` remains compatible. Mixed Native/external CRUD requests retain per-item semantics with no distributed transaction; independent relation_create/relation_delete actions can follow Provider CRUD in an explicitly non-atomic request. Request-local create clientRefs resolve after successful record creation; failed or unknown creates fail dependent relations. Provider record writes and D1 edges do not roll back together. Attached semanticRelations on a Provider create remain unavailable; use independent relation_create.

External operation audit is `pending -> succeeded | failed | unknown`. It captures verified Application/Principal/Actor/Delegation chain, operation, identity, timestamp and status; no record payload, secret or historical schema. Write audit is persisted **before** provider execution. Crash/network ambiguity remains pending/unknown; it is never reported as a guaranteed failure and never retried blindly. This is operation attribution, not Native Change/outbox or Information Provenance. Single-use delegated writes are rejected because provider success and D1 consumption cannot be atomically guaranteed. Single-use reads use the existing conditional consumption before returning data.

## Freshness and failures / 新鲜度与失败

Registration discovers once; manual refresh and a bounded scheduled reconciliation update only the latest snapshot. External runtime requires deployment-supplied `EXTERNAL_SCHEMA_REFRESH_SECONDS` (60–86400); no speculative default SLO is presented as measured. Reconciliation selects at most 20 executable due registrations through the partial next_refresh_at/model_key index, with 2 concurrent refreshes. Disabling a Connection or retiring its business definition parks its queue entries; reactivation schedules only registrations with a current published definition (legacy untyped bindings remain supported). Connection, Space and business-definition liveness filter before LIMIT. Republishing the same origin resumes eligible binding/identity queues without resetting Registry versions or deleting records. External reconciliation, Recurrence rolling and existing outbox dispatch run with independent failure isolation; all failures remain observable. No ordinary operation fetches schema first. An explicitly unexecuted schema-mismatch response permits one refresh and one retry; uncertain writes never retry. Metadata status uses current-state checks. Provider access removal and connection revoke fail closed.

For non-atomic relation batches, a Provider endpoint read failure belongs to the items depending on that endpoint. Independent Native mutations and successful endpoint items continue; Get/Query retain their strict failure semantics. Provider read audit and degraded metadata finalize in grouped D1 writes rather than one D1 update per failed endpoint.

## Relations / 关系

Published, active External business bindings participate in the same Semantic Relation API using business model keys. Source write and target read are checked before Provider resolution; grouped identity-only metadata, pending/final audit batches and <=3 concurrent Provider reads avoid per-endpoint D1 waterfalls. Native-Native commit/cleanup remains atomic. External endpoints reject atomic batch before Provider I/O, expose opaque unavailable on failed/missing hydration, and never invent Native versions. Confirmed through-LifeSpace Provider deletion invalidates observed identity and cleans local edges afterward; this local cleanup is not atomic with the Provider write. Provider-direct absence remains opaque: missing and denied cannot reliably prove deletion, so retained links can be explicitly removed under current source-write/target-read authority without contacting the Provider. Bounded periodic identity observation checks at most 20 due IDs with <=3 concurrent Provider reads, stores only availability/observation/next-check metadata, and marks missing/hidden endpoints unavailable before SQL pagination. It uses the trusted connection only for metadata observation, never saved User/Delegation tokens, and publishes no Provider payload or fabricated User attribution. Links are retained for explicit local removal; successful later reads restore availability. Queue indexes and Connection/binding parking keep disabled connections out of executable work. Actual Provider latency/freshness remains a staging gate. Legacy untyped ext_* registrations remain CRUD-only; fixed record/record_list field targets remain Native-only.

## Verification and rollout / 验证与发布

Synthetic contract/integration tests and structural call-count tests are reproducible. Provider wall latency/freshness SLO, real credential permissions and staging acceptance require an isolated deployed Adapter binding and synthetic Notion data source. Local timings are not provider p50/p95. No production docs may mark this available before successful production deployment.

Deployment wiring is code-owned by the canonical manual platform workflows. An enabled environment deploys the immutable Adapter revision in `infra/external-provider.json` before Core, injects matching independent secrets over stdin, resolves optional `EXTERNAL_ADAPTER` in the ephemeral checkout and verifies live private exposure/binding/refresh settings, the per-connection `CONNECTIONS` Durable Object binding **and** the `CONNECTION_VAULT_MASTER_KEY` secret binding. Remote profiles explicitly configure a 300-second schema refresh interval; this is configuration, not a measured SLO. Staging runs the same External and Recurrence acceptance orchestration covered by HTTP/D1 integration tests. See [deployment prerequisites and acceptance](../infra/external-provider-rollout.md) for Environment setup, automatic checks, cleanup and the separate Console browser gate. A Native-only release must not be reported as External acceptance.

Console is a first-party proving client, not a second control plane for connection state. In a Space, the user can create a provider Connection, discover accessible Provider resources, choose a published External business definition and bind it without GitHub/D1/platform-admin intervention. Those exact Space-scoped Core APIs are the intended contract for ALOHA, HomeMew and other applications. Console uses a verified User token with `spaces:manage`, never the platform executor or hidden membership. The Console Application scope ceiling must explicitly allow `spaces:manage`; provisioning/real staging verification is a release gate.
